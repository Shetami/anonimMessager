# Relay

«Слепой» сервер доставки. Он хранит публичные ключи для установки сессий и очереди зашифрованных конвертов, адресованные анонимным ID. Отправителей не знает. Логов запросов и IP-адресов не пишет. Недоставленные конверты удаляются через `-ttl` (по умолчанию 14 дней).

## API

| Метод | Путь | Аутентификация |
|---|---|---|
| POST | `/v1/accounts` | подпись новым ключом ящика |
| DELETE | `/v1/accounts` | да |
| GET | `/v1/accounts/{id}/bundle` | нет (расходует один одноразовый пре-ключ) |
| PUT | `/v1/keys` | да |
| GET | `/v1/keys/count` | да |
| PUT | `/v1/messages/{id}` | **нет**: отправитель анонимен |
| GET | `/v1/messages[?wait=N]` | да. С `wait` сервер держит запрос открытым до N секунд (максимум 25), пока в ящик не придёт конверт (long poll) |
| POST | `/v1/messages/ack` | да |
| PUT | `/v1/attachments/{id}` | **нет**: зашифрованное вложение, `id` — 32 hex-символа, выбранные клиентом случайно |
| GET | `/v1/attachments/{id}` | нет: знание случайного `id` и есть право доступа |
| DELETE | `/v1/attachments/{id}` | нет: получатель удаляет вложение после скачивания |
| GET | `/v1/turn` | нет: временные учётные данные TURN для звонков; 404, если звонки не настроены |

Аутентификация: заголовок `Authorization: Calc <id>:<unix>:<nonce>:<base64 ed25519 sig>`, подпись покрывает `method\npath\nunix\nnonce\nhex(sha256(body))`. Query-строка в подпись не входит.

Конверты в ящике выдаются строго в порядке поступления (FIFO), даже если пришли в одну секунду. На этом держится сигнализация звонков: offer должен прийти раньше своих ICE-кандидатов.

## Вложения

Файлы хранятся в каталоге `-attachments` (по умолчанию `./attachments`) как непрозрачные блобы. Клиент шифрует каждый файл отдельным ключом и дополняет его до размера с шагом 5%. Ключ передаётся только внутри E2E-сообщения. Невостребованные вложения удаляются через тот же `-ttl`.

| Флаг | По умолчанию | |
|---|---|---|
| `-max-attachment` | 110 МБ | максимум для одного зашифрованного файла (клиент ограничивает исходный файл 100 МБ) |
| `-attachments-quota` | 20 ГБ | сколько всего вложений сервер хранит одновременно; при переполнении отвечает 507 |

Если перед сервером стоит прокси, поднимите у него лимит размера тела запроса: например, в nginx `client_max_body_size 110m;`. Caddy по умолчанию размер не ограничивает. Таймаут ответа у прокси должен быть больше 25 секунд из-за long poll; значения по умолчанию у nginx (60 с) и Caddy подходят.

## Звонки

Звонки идут через [RingRTC](https://github.com/signalapp/ringrtc), ту же библиотеку, что в Signal. Сигнализация (offer, answer, ICE, hangup) — это обычные E2E-сообщения в запечатанных конвертах, так что relay не отличает звонок от текста. Медиа (SRTP, шифрование между устройствами) всегда идёт через TURN-сервер, поэтому собеседники не узнают IP-адреса друг друга. Без TURN звонки не работают: прямого P2P-режима в приложении нет намеренно.

1. Поставьте [coturn](https://github.com/coturn/coturn) на отдельный хост или рядом с relay. Ему нужны UDP 3478, TCP 443 (TURN over TLS) и UDP-диапазон relay-портов (по умолчанию 49152–65535).
2. Возьмите за основу [deploy/turnserver.conf](deploy/turnserver.conf): там отключены все логи, запрещён relay во внутренние сети и включены квоты. Задайте `realm`, пути к сертификату и общий секрет:
   ```sh
   openssl rand -hex 32 > /etc/relay/turn-secret   # то же значение в static-auth-secret
   ```
3. Запустите relay с параметрами TURN:
   ```sh
   ./relay ... -turn-secret-file /etc/relay/turn-secret \
     -turn-urls 'turn:turn.example.com:3478?transport=udp,turns:turn.example.com:443?transport=tcp'
   ```

| Флаг | По умолчанию | |
|---|---|---|
| `-turn-secret-file` | — | файл с `static-auth-secret` coturn; без него `/v1/turn` отвечает 404 |
| `-turn-urls` | — | адреса TURN через запятую, передаются клиентам как есть |
| `-turn-ttl` | 12 ч | срок действия выданных учётных данных. Клиент кэширует их и обновляет, когда остаётся меньше 2 часов, поэтому один звонок гарантированно длится до 2 часов |

`/v1/turn` не требует аутентификации: иначе relay знал бы, какой ящик собирается звонить. Клиенты запрашивают учётные данные заранее, при фоновой синхронизации, а не в момент звонка, чтобы и время запроса ничего не выдавало. Обратная сторона: кто угодно может получить учётные данные и гонять трафик через ваш TURN. Квоты в `turnserver.conf` это ограничивают; при публичном запуске добавьте rate limit на прокси перед `/v1/turn`.

## Развёртывание

Вариант со встроенным TLS:

```sh
go build -o relay ./cmd/relay
./relay -addr :443 -db /var/lib/relay/relay.db -tls-cert fullchain.pem -tls-key privkey.pem
```

Вариант за Caddy. Логирование **должно быть выключено**: Caddy не пишет access-логи, пока их явно не включить, поэтому не добавляйте директиву `log`.

```
relay.example.com {
	reverse_proxy 127.0.0.1:8080
}
```

```sh
./relay -addr 127.0.0.1:8080 -db /var/lib/relay/relay.db
```

SPKI-пин для [AppConfig.swift](../ios/Calculon/App/AppConfig.swift):

```sh
openssl x509 -in cert.pem -pubkey -noout | openssl pkey -pubin -outform der \
  | openssl dgst -sha256 -binary | base64
```

Пиньте ключ, а не сертификат, и держите резервный ключ. Для Let's Encrypt используйте `--reuse-key`, иначе ключ меняется при каждом продлении.

Рекомендации для хоста: шифрование диска, отключённый swap или зашифрованный swap, минимум сервисов, не хранить бэкапы `relay.db`. Там только транзитные данные, их потеря ничего не ломает.
